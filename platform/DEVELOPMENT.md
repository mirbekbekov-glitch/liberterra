# CRM: сборка и изолированный стенд

Рабочая ветка: `crm/production-baseline-20261027`. Команды выполняются из корня репозитория с Node.js 24.20.0. Установка пакетов, ключи и доступ к интернету не нужны.

```powershell
node platform/scripts/build.cjs
node platform/scripts/verify-source.cjs
node --test platform/tests/*.test.cjs
node platform/dev/server.cjs
```

Откройте `http://127.0.0.1:4173/`, выберите «Агент A». Создайте клиента, затем сделку. Второй агент имеет отдельные записи, «Без допуска» получает отказ. Остановка сервера: Ctrl+C. Другой порт: `node platform/dev/server.cjs 4174`.

## Исходники и воспроизводимость

- `workers/` — неизменяемые шаблоны опубликованных Worker. Их SHA-256 проверяется перед каждой сборкой. Рабочие результаты находятся в `dist/workers/`.
- `assets/` — 192 файла, извлечённых из четырёх встроенных карт ресурсов (`files` в обоих Worker, `crmAssetPatch` и `crmWorkflowAssets` в backend). Карты читаются с любыми кавычками, включая шаблонные строки без подстановок. `assets.json` фиксирует происхождение и первоначальные хеши. Одноразовый `extract-assets.cjs` уже выполнен и отказывается перезаписывать манифест.
- Фильтр «Источник» определяет принадлежность объекта по данным фида: `listing_agent_phone` (сравнивается с телефоном агента из профиля) и имя агента из `contact_name`, когда объявление размещено агентом. Агентство фид не отдаёт: оно берётся из `/api/public-agents` по имени агента. Как только в фид добавят `listing_agent_name` и `listing_agent_agency`, код возьмёт их напрямую — эти поля уже читаются первыми.
- Сам фильтр — выпадающая панель (кнопка `#heroSourceToggle`, панель `#heroSourcePanel`): поиск по сотрудникам, три группы (`state.source`) и список риэлторов (`state.sourceStaff` — массив ключей `normalizeSearch(имя)`, в URL `staff=a,b`). Отметки складываются, а не пересекаются: объект проходит, если попал хотя бы в одну. Список строится из `/api/public-agents` (имя, агентство, фото) и имён в текущей выдаче, число рядом с именем — объекты по выбранному типу сделки. Телефонов в публичном реестре нет, показывать их тут нечем.
- Селекторы панели обязаны начинаться с `.v20-source`: `.v20-main label{display:block}` специфичнее одиночного класса и разворачивает строки списка в столбик.
- Не каждый файл карты отдаётся из карты: часть маршрутов перекрыта присваиваниями, часть собирается на лету, а три CSS подключены как `media="print"` и на экране не действуют. Список, причины и порядок проверки — в разделе «Какие файлы отдаются не из карты ресурсов».
- CRM UI редактируется в `assets/backend/crmWorkflowAssets/`. Новая воронка и рабочий день находятся в `features/deals.js` и `features/deals.css`; `features.json` подключает их к существующим ресурсам, без новых production-маршрутов.
- `apps-script/` — все 13 файлов живого проекта, снятые через Apps Script API (версия 97). `public/` и `provenance.json` — HTTP-снимок.
- `dist/build-manifest.json` содержит хеши выходных файлов без даты, случайных ID и абсолютных путей. Две чистые сборки и повторная сборка проверяются автоматическим тестом. Не кладите ручные файлы в `dist`: неизвестные файлы останавливают повторную сборку.

Извлечение и обратная сборка воспроизводят опубликованный site Worker побайтно: SHA-256 `b70b238201527f058505b5283d9718577626c632c87b99283f01f6320e14fdc5` совпадает с активной версией. Backend отличается намеренно: `features.json` добавляет невыложенную воронку сделок, поэтому его сборка не равна активному `45d8ee65402331fbdbea4aafc7e1adf38f8a835f9d117edb840553090480439a`. Исходные Worker и публичный снимок не изменены. `verify-source --baseline` предназначен для исходного коммита, а не для изменённого Apps Script.

## Какие файлы отдаются не из карты ресурсов

Проверено 17 ноября 2026 года на активной версии `99312995`. Повторить: `node platform/scripts/audit-embedded.cjs` — скрипт разбирает карту, собирает присваивания, скачивает каждый текстовый файл с боевого URL и печатает «совпало N, разошлось M» со списком. Он только читает.

На момент проверки: 88 записей, совпали 72, разошлись 15.

**Правка файла в `assets/site/files/` доходит до сайта только тогда, когда карта и есть источник.** В остальных случаях правка собирается в бандл, выкладывается, меняет SHA — и не меняет на сайте ничего.

### Четыре способа разойтись с картой

**1. Присваивание после карты.** Ниже по коду стоит `files["/путь"]="…"`, выигрывает последнее. Двенадцать ключей: `/`, `/contact-gate.js`, `/favicon.png`, `/index.html`, `/login.html`, `/onboarding.css`, `/onboarding.js`, `/profile`, `/profile.html`, `/profile.js`, `/telegram-membership.js`, `/user-registration.js`. Ключ может присваиваться и дважды (так у `/favicon.png`) — выигрывает последнее присваивание, правка первого так же мертва, как правка карты. Менять нужно присваивание в `workers/site.mjs`: `/profile.js` в карте 51 007 байт, отдаётся 69 433 из присваивания.

**2. Подстановка на лету.** Обработчик собирает ответ из нескольких источников:

- *Каталожные страницы.* Обработчик `script[src]` удаляет тег `/script.js` и вставляет вшитую в код Worker копию того же бандла (строка рядом с `dataset.catalogScriptStartedMs`, заканчивается `</script>`). Поэтому `/agents.html`, `/calculator.html`, `/catalog.html`, `/district-map.html`, `/mortgage.html`, `/newbuilding.html`, `/newbuildings.html`, `/object.html`, `/requests.html` отдаются примерно вдвое больше карты. Менять нужно обе копии, и закрывающий `</script>` во вшитой копии обязан сохраниться, иначе страница ломается целиком.
- *`/site-theme.css`.* В Worker три копии под этим ключом: 932 646 байт в карте и две одинаковые по 34 626 рядом с `criticalStyles`. Отдаётся ни одна из трёх: живой файл — это копия на 34 626 плюс вставленная при запросе строка `:root{--lt-victory-hero:url("…")}` в середине.

**3. Дублирование ключа.** `/site-theme.css`, `/style.css` и `/v20-global.css` встречаются в теле Worker по три раза, остальные 85 файлов — по одному. У `/style.css` и `/v20-global.css` первая копия совпадает с боем побайтно, у `/site-theme.css` — нет. По месту в файле угадать нельзя, только сравнением хешей.

**4. CSS: страница применяет не файл, а его вшитую копию.** Самый тихий случай: правка доезжает до браузера и всё равно ничего не делает. На публичных страницах Worker инлайнит `<style data-lt-public-critical-style>` из структуры `criticalStyles`, а настоящие ссылки переводит в `media="print"`, то есть на экране они не действуют вовсе:

| Инлайновый блок | Источник | Ссылка |
| --- | --- | --- |
| 174 364 символа | `style.css` | `media="print"` |
| 34 622 символа | `site-theme.css` | `media="print"` |
| 13 078 символов | `v20-global.css` | `media="print"` |

Копии в `criticalStyles` живут отдельно от карты и расходятся с ней: у `/v20-global.css` в карте 14 478 символов, в `criticalStyles` — 13 078 устаревших. Правка карты меняет файл по URL и не меняет страницу. Менять нужно обе копии `criticalStyles`.

Ключ `/v20-global.css` встречается в Worker четырежды: карта, две копии `criticalStyles` и упоминание в списке `publicAssets`.

Работают листы, подключённые без `media`: `dual-price.css`, `request-cards.css`, `agent-photo.css`, `leaflet.css`, `auth-entry.css` — но ни один не подключён на всех страницах, общего рычага среди них нет.

### Правило перед каждой правкой встроенного файла

1. Скачать файл с боевого URL.
2. Сравнить SHA-256 с той копией, которую собираетесь менять. Не совпало — вы правите мёртвую копию, ищите источник дальше.
3. **Для CSS проверка по файлу ничего не доказывает.** Страница применяет инлайновые копии из `criticalStyles`, а ссылки переведены в `media="print"`, поэтому свежий файл по URL может соседствовать с устаревшей применяемой копией. Единственная надёжная проверка — computed style на живой странице: открыть её в браузере нужной ширины и прочитать у элемента то свойство, которое правили.
4. После выкладки скачать боевой URL ещё раз и убедиться, что отдаётся залитое, а для CSS — ещё раз снять computed style.

Четвёртый шаг нужен не только из-за копий: выкладки идут параллельно, и чужая заливка затирает вашу молча. Так 17 ноября в 16:50 потерялась правка, залитая за 0,8 секунды до чужой.

## Изоляция

Стенд слушает только loopback. HTTP Host и Origin проверяются. Browser CSP разрешает подключения только к этому origin. API не проксируется на рабочий сайт; неизвестные действия недоступны. Сервер исполняет настоящий CRM gateway и Apps Script workflow в VM с синтетическими идентификаторами, каталогом и адаптером Sheets; внешние запросы адаптера запрещены. Это тестовая замена авторизации и инфраструктуры, не проверка настоящих Telegram/email-сессий, Google Sheets или Cloudflare bindings. Остальные разделы платформы здесь не эмулируются полностью.

Фикстуры двух агентов и нескольких объектов явно тестовые. CRM-записи хранятся в `platform/.sandbox/sheets.json` (игнорируется Git). Одновременный запуск с тем же каталогом блокируется `server.lock`. После аварийного завершения убедитесь, что прежний процесс остановлен, прежде чем удалять оставшийся lock. Для нового набора данных при остановленном сервере переименуйте `.sandbox`, сохранив старый набор как резервную копию. Не вводите настоящие персональные данные в стенд.

## Первое улучшение CRM

«Рабочий день» показывает активные сделки, финальные этапы, задачи на сегодня и просрочки по времени Бишкека. Плановые комиссии суммируются раздельно по USD/KGS и не считаются полученным доходом. До загрузки задач отображается неизвестное состояние, а не ложный ноль.

«Сделки» — отдельные записи `kind=deal`, связанные с собственным клиентом и доступным объектом. Десять этапов: новый лид, квалификация, подбор, назначен показ, показ проведён, переговоры, согласование, документы, успешно закрыта, проиграна. Разрешены соседний следующий/предыдущий этап и потеря; успешное закрытие — из документов. Успех требует объекта и положительной суммы, потеря — причины. Терминальные этапы нельзя переоткрывать; остальные поля редактируются. На широком экране доступно перетаскивание, на телефоне — выбор этапа и форма. Переходы всегда проверяет сервер.

Сохранены проверки роли/владельца, блокировка, версия и idempotency. История фиксирует автора, серверное время, переход и имена изменённых полей. Она ограничена 100 событиями и размером записи 45 000 символов: превышение отклоняет запись, не стирая историю. Отдельный долговременный журнал и управляемое переоткрытие сделок — следующие этапы разработки. История не хранит предыдущие значения всех полей и не является финансовым аудитом.

## Выпуск и откат

Сайт — это Worker `liberterra-listing-ui`: публичные HTML, CSS и JS встроены в него. Правка файла в `assets/site/files/` попадает на сайт только после пересборки и заливки этого Worker. Backend `hidden-pine-cbff` выкладывается отдельно и сейчас выкладке не подлежит (см. «Чего не делать»).

Нужны: Node.js 24, доступ к ветке `crm/production-baseline-20261027`, токен Cloudflare с правом **Workers Scripts: Edit** на аккаунт `c94bdedbc72dfa6205338f6b0c47f22c` (создаётся в Cloudflare → My Profile → API Tokens → Create Token → шаблон «Edit Cloudflare Workers»; значение показывается один раз).

### 1. Собрать из ветки

```
git checkout crm/production-baseline-20261027 && git pull
node platform/scripts/build.cjs
node platform/scripts/verify-source.cjs
node --test platform/tests/*.test.cjs
```

`build.cjs` печатает `baselineEqual` по каждому Worker. Для `site` он показывает, равна ли сборка захваченному шаблону: `true` — вы собрали ровно то, что уже выложено, выкладывать нечего; `false` — в `assets/site/files/` есть правки, их и выкладываем.

Из-за этого `sandbox.test.cjs` («reproducible build with frozen Worker templates») проверяет `site baselineEqual === true` и проходит только на нетронутом дереве: пока ваша правка не выложена и шаблон не перезахвачен, этот тест падает — это ожидаемое состояние, а не поломка. Порядок такой: правка → тест падает на этой проверке, остальные шесть зелёные → выкладка → перезахват шаблона → все семь снова проходят. Если упал любой другой тест — выкладывать нельзя. Тесты должны пройти все.

### 2. Сверить с тем, что крутится сейчас

Выкладка затирает Worker целиком, поэтому до неё убеждаемся, что никто не менял его мимо репозитория:

```
ACC=c94bdedbc72dfa6205338f6b0c47f22c
curl -sS "https://api.cloudflare.com/client/v4/accounts/$ACC/workers/scripts/liberterra-listing-ui" \
  -o /tmp/live.multipart
```

Из ответа (multipart) берём часть `worker.mjs` и считаем её SHA-256:

```
python3 -c "import hashlib;raw=open('/tmp/live.multipart','rb').read();b=raw.split(b'\r\n',1)[0];print(hashlib.sha256(raw[raw.index(b'\r\n\r\n')+4:raw.rindex(b'\r\n'+b+b'--')]).hexdigest())"
```
 Он обязан совпасть с полем `sha256` для `liberterra-listing-ui` в `provenance.json`. Не совпал — **не выкладывайте**: продакшен ушёл вперёд, сначала выровняйте репозиторий (захватить активные версии в `workers/`, переизвлечь ресурсы, пересчитать `provenance.json`), иначе заливка откатит чужую работу.

### 3. Залить site Worker

```
ACC=c94bdedbc72dfa6205338f6b0c47f22c
cat > /tmp/meta.json <<'JSON'
{"main_module":"worker.mjs","compatibility_date":"2026-07-03","compatibility_flags":[],
 "bindings":[{"type":"service","name":"BACKEND","service":"hidden-pine-cbff","environment":"production"},
             {"type":"version_metadata","name":"LT_ASSET_RELEASE"}]}
JSON
curl -sS -X PUT "https://api.cloudflare.com/client/v4/accounts/$ACC/workers/scripts/liberterra-listing-ui" \
  -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  -F "metadata=@/tmp/meta.json;type=application/json" \
  -F "worker.mjs=@platform/dist/workers/site.mjs;filename=worker.mjs;type=application/javascript+module"
```

Три места, где легко ошибиться: `filename=worker.mjs` обязателен — иначе Cloudflare отвечает `No such module: worker.mjs`; `bindings` надо передать целиком, пропущенная привязка отключит CRM и каталог; `compatibility_date` менять не надо.

### 4. Проверить и записать

```
curl -s "https://liberterra.kg/?cb=$RANDOM" | grep -c <признак правки>
curl -s "https://liberterra.kg/catalog.html" | grep -c <признак правки>
```

Затем в том же коммите или следующем обновить `provenance.json`: новые `version`, `sha256`, `capturedAt` у `liberterra-listing-ui` (id версии — `.../versions?per_page=1`). Без этого шаг 2 в следующий раз даст ложную тревогу.

### 5. Откат

Cloudflare хранит версии: панель → Workers & Pages → `liberterra-listing-ui` → Deployments → Rollback на предыдущую версию. Это быстрее и надёжнее повторной сборки. После отката верните `provenance.json` к той же версии.

### Ручные выкладки владельца

Владелец сайта выкладывает Worker и сам, помимо сессий. Такая выкладка не проходит шаги выше, поэтому после неё ветка отстаёт: нужен перезахват (выгрузить активную версию в `workers/`, переизвлечь ресурсы, пересчитать `provenance.json`). Пример: 17 ноября значение по умолчанию в каталоге меняли вручную с `deals: ["продажа"]` на `["аренда"]` — правку пришлось вносить дважды, сначала в карте ресурсов, затем во вшитой копии бандла, иначе страницы её не видели.

### Чего не делать

- **Не править Worker в панели Cloudflare и не заливать его мимо ветки.** Любая такая правка делает следующую сборку из репозитория откатом сайта.
- **Не выкладывать backend**, пока `features.json` добавляет невыложенную воронку сделок: его сборка намеренно не равна активной версии. Выпуск сделок — отдельная задача с проверкой Apps Script и листа CRM.
- Не заливать `dist/` руками и не класть в него свои файлы: повторная сборка остановится на неизвестном файле.

Изменение хранения добавочное: новый тип в существующем листе CRM Workflow, без удаления или преобразования записей клиентов. Сначала обновляется Apps Script с поддержкой `deal_stages` и `deal`, затем собранный backend Worker. Старый сервер не должен получать новую форму: UI без метаданных этапов блокирует создание сделки. При откате сохраняются все строки сделок; нельзя очищать лист. Старый интерфейс не показывает новый тип, поэтому перед откатом нужен экспорт и план сохранения доступа к этим данным.

### Как править Apps Script из сессии

Нужен OAuth-токен владельца со scope `script.projects` и `script.deployments` (OAuth Playground; в настройках `script.google.com/home/usersettings` должен быть включён Apps Script API). Токен сохраняется как network secret на хост `script.googleapis.com` и живёт час.

```
GET  https://script.googleapis.com/v1/projects/{scriptId}/content     # прочитать все файлы
PUT  https://script.googleapis.com/v1/projects/{scriptId}/content     # записать (files целиком)
POST https://script.googleapis.com/v1/projects/{scriptId}/versions    # создать версию
PUT  https://script.googleapis.com/v1/projects/{scriptId}/deployments/{deploymentId}
```

`scriptId` и `deploymentId` лежат в `provenance.json` → `appsScript`. Обновлять нужно **существующее** развёртывание «Воронка сделок»: у нового будет другой URL, которого Worker не знает. В `PUT content` передаётся весь массив `files` — читайте, меняйте нужные, отправляйте все.

Чего API не даёт: запуск функции (`scripts.run` требует ещё и собственные разрешения скрипта — таблицы, почта). Разовые `backfill*` запускаются вручную в редакторе.

## Сверка с боем: развёрнутая версия против загруженной

`GET /workers/scripts/{имя}` отдаёт **последнюю загруженную** версию, а не ту, что обслуживает запросы. Обычно это одно и то же, но не всегда: развернуть можно и не последнюю загрузку — откатом через `/deployments` или выкладкой через versions API. В такие минуты тело из `GET` — не то, что видят посетители, и снимок, снятый по нему, лжёт, проходя все проверки.

Случай 18 ноября: в 18:31:12 загружена и развёрнута версия 698 (`99be48c9`), в 18:32:33 развёрнута более ранняя 696 (`4486d197`, загружена в 18:17:57) — так возвращали блок звонков. До 18:41:56 загруженная и развёрнутая расходились. Перезахват `fd75ee0`, сделанный в 18:38, записал в `provenance.json` SHA загруженной версии `2cc69a2d…`, тогда как отдавалась 696. Ошибка прожила до следующего перезахвата `c68cd06` и больше ни на что не повлияла, но проверки её не поймали — им нечем.

Поэтому перед каждым захватом сравнивайте:

```
ACC=c94bdedbc72dfa6205338f6b0c47f22c
curl -sS ".../workers/scripts/$W/versions?per_page=1"   # последняя загруженная
curl -sS ".../workers/scripts/$W/deployments"           # текущее развёртывание
```

Совпали — тело из `GET /workers/scripts/$W` достоверно. Разошлись — захват делать нельзя: сначала дождитесь, пока владелец совместит их новой заливкой, либо берите источник другим путём. Содержимое произвольной версии через API не выгружается: `/versions/{id}` отдаёт метаданные и список ресурсов, но не модули.

У `liberterra-listing-ui` есть вторая, независимая проверка: привязка `version_metadata` подставляет id развёрнутой версии в `_ltv` у ссылок на страницах, то есть отвечает сам работающий код. У `hidden-pine-cbff` такой привязки нет — именно там слепое пятно, и именно там оно сработало.

## Ожидание при публикации объявления

Публикация с пятью фотографиями занимает десятки секунд. 18 ноября оба конца этого ожидания были закрыты; раздел оставлен, потому что числа связаны между собой и ломать их по одному нельзя.

**Backend.** Запрос `create_web_listing` к `ACCOUNT_WEBHOOK_URL` в `handleSubmissions` идёт с `AbortSignal.timeout(45e3)` — предел выбран так, чтобы хватало на загрузку пяти фотографий в Drive. Раньше его не было вовсе, в отличие от `confirmSavedSubmission` с её двадцатью секундами, поэтому вызов висел до платформенного предела и восстановление начиналось неизвестно когда. После обрыва идёт цикл восстановления: до четырёх проверок с паузой 4 секунды, с общим пределом 20 секунд от начала цикла (проверка предела стоит после вызова и перед следующей паузой, поэтому лишняя пауза не берётся). Итог предсказуем: 45 секунд на публикацию плюс не больше двадцати с небольшим на восстановление.

**Site.** `add-object.js` меняет надпись на кнопке двумя ступенями: через 10 секунд «Отправляем фотографии, это может занять до минуты…», через 45 — «Проверяем, сохранился ли объект…». Вторая ступень приурочена к сроку `AbortSignal` не случайно: ровно тогда на сервере начинается `confirmSavedSubmission`. Одной ступени мало — на десятой секунде идёт обычная загрузка, и сообщение о проверке сохранности пугало бы на ровном месте. Оба таймера снимаются в `finally`, туда же возвращается «Отправить на проверку», поэтому надпись восстанавливается при любом исходе.

Если будете менять 45 секунд, поменяйте и вторую ступень в `add-object.js`: иначе подсказка снова разойдётся с тем, что происходит на сервере.

### Как править такие файлы

Присваивания после карты теперь разбираются и собираются обратно, поэтому у них есть обычный источник.

```powershell
node platform/scripts/find-dead-map-entries.cjs   # посмотреть список ключей
node platform/scripts/build.cjs
node --test platform/tests/assignments.test.cjs
```

- `assets/<bundle>/assign/<карта>/<ключ>` — значения, которые Worker присваивает после карты. Ключ `/` лежит под именем `__root__`. Правится как обычный файл.
- `assignments.json` — манифест: SHA-256 шаблона, с которого снято, и контрольная сумма каждого файла. Считайте её на байтах файла, без перевода переводов строк: часть страниц содержит CRLF.
- `scripts/extract-assignments.cjs` — одноразовое извлечение; существующий манифест не перезаписывает. Нужен после пересъёмки Worker.
- `build.cjs` подставляет значения на место: сначала литералы карт, затем присваивания, в порядке убывания смещения. Если содержимое не изменилось, литерал пишется обратно дословно, поэтому побайтная сборка site Worker сохраняется.

Дописанное через `features.json` теперь идёт в то значение, которое реально отдаётся, а не в запись карты. Отсюда два следствия, оба проверены 18 ноября.

**Фича может уже быть внутри.** Воронку сделок когда-то дописали прямо в Worker, поэтому она есть в присваивании на бою и, значит, в снимке `assign/`. Пока append шёл в мёртвую копию карты, запись в `features.json` была безвредна; как только он пошёл в отдаваемое значение, та же запись стала дублировать фичу — в сборке получались две доски сделок и два слушателя. Поэтому записи `crm-workflow.js -> features/deals.js` и `crm-workspace.css -> features/deals.css` из `features.json` убраны, а `build.cjs` перед записью проверяет, не содержится ли текст фичи в значении, и падает с явным сообщением. Инвариант: снимок `assign/` — это база без фич, фичи приходят из `features.json`. После перезахвата это надо перепроверять: фича, выложенная напрямую, окажется внутри снимка.

**Снимок может отставать от боя.** `assign/crmWorkflowAssets/crm-workflow.js` снят с захваченного шаблона, а боевой Worker ушёл вперёд: в живом файле есть блок звонков клиента из телефонии (`crm-deal-calls`, `callNotes`), которого в шаблоне нет — 150 014 символов против 148 185, общий префикс 50 127. Сборка backend из такого снимка откатила бы телефонию. Перед выкладкой backend сравнивайте собранное значение с живым файлом, а не только с маркерами фич.

Правило проверки из раздела выше не отменяется: для CSS по-прежнему доказательством служит только computed style на живой странице.
