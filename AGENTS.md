# Liberterra: инструкции для агентов

## Область production baseline

Для разработки действующей платформы используйте `platform/`, его `README.md`, `provenance.json` и `AGENTS.md`. Правила статического одностраничного демо ниже относятся к корневому `index.html`; внутри `platform/` действуют отдельные инструкции для Worker, Apps Script и CRM. Не переносите демо поверх production.

## Контекст и границы

- Перед работой читай `README.md` и относящиеся к задаче разделы `CLAUDE.md`; проверяй фактический код `index.html`, если описание и код расходятся. Отвечай пользователю по-русски.
- Текущая версия — статическое демо в одном `index.html`: HTML, CSS и обычный JavaScript без сборки и пакетов. Не добавляй зависимости, сервер или внешние сервисы ради локальной правки демо. Для рабочего входа, CRM, модерации и хранения данных требуется отдельная серверная задача.
- Объекты, агенты, контакты и цифры в демо вымышлены; формы ничего не отправляют, переключатель роли не подтверждает полномочия, иллюстрации заменяют фото, карта условная. Не выдавай эти элементы за реальные функции или данные; сохраняй маркировку «(демо)» там, где действие не выполняется.
- Меняй только то, что нужно для запроса. Не публикуй и не подключай реальные данные или сервисы без задачи на это. Различай подготовленное локально, опубликованное и проверенное в работающей среде.

## Автоматический выбор локальных Skills

Для каждой задачи до редактирования определи затронутые области и прочитай соответствующий `SKILL.md` из `.agents/skills`. Используй несколько навыков, если задача пересекает области; не загружай все шесть для несвязанной задачи. Явное указание пользователя на навык имеет приоритет. Копии в `.claude/skills` сохранены как исходники; рабочий каталог навыков для Codex — `.agents/skills`.

| Задача | Навык |
| --- | --- |
| Интерфейс, верстка, мобильная версия, формы, тексты кнопок, доступность, Telegram Mini App UI | `liberterra-ux-ui` |
| Кабинет агента, клиенты, объекты, сделки, задачи, права на CRM-данные | `liberterra-agent-crm` |
| Вход через Telegram или телефон, сессии, роли, заявка и одобрение агента | `liberterra-auth-onboarding` |
| Реальная карта, координаты, геокодирование, маркеры, фильтр по области | `liberterra-map` |
| Очередь проверки, Telegram-бот модератора, решения по заявкам и объектам | `liberterra-moderation-telegram` |
| Телефония, вебхуки АТС, записи и экран звонков | `liberterra-calls` |

Если навык ссылается на другой навык, которого нет в текущей среде, выполни применимые проверки доступными средствами и сообщи об ограничении. Навыки направляют реализацию, но не разрешают сами по себе развёртывание, отправку данных или смену продукта.

## Код и безопасность

- Сохраняй текущую архитектуру, если задача не требует её изменения: маршруты через hash и `render()`, действия через `data-a` и объект `A`, фильтры через `data-f`, состояние `S` и сохранение в `localStorage` под ключом `lt2`. При новом сохраняемом поле обновляй и загрузку, и `save()`.
- Для пользовательского и CSV-текста в HTML-шаблонах используй `esc()`; не вставляй непроверенный HTML. При изменении `parseCSV()` проверяй недоверенные значения и поведение при ошибке загрузки.
- Не храни токены, секреты, приватные ключи или реальные персональные данные в `index.html`, репозитории и клиентском `localStorage`. Клиентская проверка роли служит только демонстрации; доступ к реальным данным, Telegram `initData`, вебхуки и решения модератора проверяются на сервере.
- Для операций с персональными данными и записями звонков следуй профильным навыкам: минимальный доступ, аудит, ограниченный срок хранения и проверка актуальных юридических требований до рабочего запуска.
- Не меняй демонстрационный курс, комиссию, даты и контактные поля в `CONFIG` на предполагаемые рабочие значения. Уточняй реальные значения перед подключением.

## UI/UX и проверка

- При изменении интерфейса применяй `liberterra-ux-ui`: сначала ширина 360–414 px, затем широкий экран; сохраняй видимость признака проверки объекта, дат актуальности, условий комиссии и путей связи. Проверяй клавиатуру, видимый фокус, подписи кнопок и понятные пустые и ошибочные состояния.
- Перед правкой найди связанный код и проверь последствия для других маршрутов, роли агента, фильтров, валюты и избранного. Не заменяй частичное обновление фильтров полным `render()` без необходимости, чтобы не терять фокус ввода.
- Проверяй изменения соразмерно задаче: синтаксис изменённого JavaScript доступными локальными средствами, открытие `index.html` в браузере, затронутые маршруты и действия, мобильный размер и консольные ошибки. Для логики добавляй тест только там, где он проверяет значимое поведение; не вводи сборку или зависимости ради тестов.
- Перед отчётом проверь итоговые файлы и сообщи, что именно изменено, какие проверки выполнены и что осталось непроверенным. Не называй локальную проверку доказательством публикации.

## Plugins и внешние инструменты

- Используй доступный инструмент по реальной задаче, после проверки его наличия: Product Design или Figma для макетов и UX; браузерный Computer Use для визуальной проверки; Firecrawl для актуальных внешних источников и SEO-исследования; Supabase для явно выбранной базы и авторизации; Google Drive/Sheets для разрешённой работы с таблицами; GitHub для удалённого репозитория; Sites только для задачи на сайт в Sites. Для актуальной документации и условий внешних API обращайся к официальным источникам.
- Plugin не является причиной менять архитектуру или отправлять проектные, клиентские либо секретные данные наружу. Используй подключённый сервис только в пределах задачи и разрешённого доступа. Не считай наличие Plugin доказательством, что сервис уже связан с этим демо.
